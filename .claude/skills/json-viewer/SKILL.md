# SKILL: JSON Viewer（案件が出す JSON を読む）

呼ばれたら、案件の JSON を人が読める形にして見せる。読み手は走行を振り返る人——課長・PM・
開発者のいずれもありうる。

---

## 呼ばれたらすること

### 1. 対象を決める

引数があれば、それが対象。案件名（`260815_01`）でもパスでもよい。案件名で渡されたときは
`$LAYER_DIR/projects/<案件名>/output` に読み替える。**引数があるときは、次の質問をしない。**

引数が無ければ、案件の候補を新しい順に4件まで集める。

```bash
ls -dt "$LAYER_DIR"/projects/*/ 2>/dev/null | head -4 | while read -r d; do
  name=$(basename "$d")
  when=$(date -r "${d%/}" "+%Y-%m-%d")
  q=$(python3 -c "import json,sys;print(json.load(open(sys.argv[1])).get('policy_question','')[:60])" \
       "$d/output/requirements_summary.json" 2>/dev/null || echo "(要件ファイルなし)")
  echo "$name | $when | $q"
done
ls -d "$LAYER_DIR"/projects/*/ 2>/dev/null | wc -l   # 総数
```

集めた候補を `AskUserQuestion` で尋ねる。選択肢は最大4件で、自由入力の「その他」は自動で
付くので、5件目以降の案件は利用者がそこに案件名を打てば指定できる。

- `header` は `案件`
- 各選択肢の `label` は案件名（`260815_01`）
- 各選択肢の `description` は `<更新日> — <policy_question>`。要件ファイルが無い案件は
  `<更新日> — (要件ファイルなし)`
- 総数が4件を超えるときは、質問文に「他 N 件は『その他』に案件名を入力」と添える

候補が0件のときは質問せず、`projects/` に案件が無いことを伝えて終わる。
候補が1件のときも質問せず、その案件を使い、どれを使ったかを相手に伝える。

利用者が「その他」に打った文字列は、案件名として `projects/` の下に実在するかを確かめる。
無ければ、実在する案件名の一覧を見せて、もう一度尋ねる。**推測で近い名前に読み替えない。**

### 2. 出す前に、必ず行数とバイト数の両方を測る

**この道具の出力は、そのまま会話に貼れる量を平気で超える。**実在の案件で測ると、案件フォルダ
をそのまま出せば 3,064 行・296KB、`--all` なら 4,787 行・542KB ある。出してから長すぎたと
気づいても、もう会話に載っている。

**行数だけで測ってはいけない。**このデータは、一つの項目に数千字が1行で入る——`analysis_brief`
の `notes` は 2,387 字、各タスクの `rationale` は 1,800〜4,500 字で、いずれも改行が無い。
実例として `analysis_brief.json --depth 3` は **74 行しかないのに 65.9KB** ある。行数を見て
「短い」と判断すると外す。

```bash
V() { bash "$LAYER_DIR/tools/run" render_json.py "$@" 2>/dev/null; }
V "$OUT" --depth 1 | wc -lc      # 行数 と バイト数
```

測った結果で、こう分ける。**両方の条件を見る。**

| 測った量 | どうするか |
|---------|-----------|
| 120 行以下 **かつ** 8KB 以下 | そのまま会話に出す |
| どちらかが超える（300 行・30KB には届かない） | 梯子を一段狭める。狭められないなら、要点を抜いて示す |
| 300 行超 **または** 30KB 超 | **会話に出さない。**ファイルに保存して添付し、要点だけを会話に書く |

これは `--depth 1` のときも、`--depth 2` のときも、`--all` のときも、1本を開くときも、
例外なく効く。

### 3. 梯子を使って、狭いほうから広げる

上ほど狭い。測った量に合う段から始め、足りなければ一段広げる。

**案件フォルダ全体**

| 段 | コマンド | 行 / バイト |
|----|---------|------------|
| 見出しだけ | `V "$OUT" \| grep -E '^## '` | 18 行 / 982 B |
| `--depth 1` | | 251 行 / 27.2KB |
| `--depth 2` | | 783 行 / 49.7KB |
| 全文 | | 3,064 行 / 296KB（`--all` 4,787 行 / 542KB） |

**1本のファイル**

| 段 | `analysis_output.json` | `analysis_brief.json` |
|----|------------------------|------------------------|
| `--depth 1` | 12 行 / 337 B | 13 行 / 6.4KB |
| `--depth 2` | 37 行 / 769 B | 49 行 / 7.1KB |
| `--depth 3` | 261 行 / 53.9KB | **74 行 / 65.9KB** |
| 全文 | 1,568 行 / 99KB | 118 行 / 66.9KB |

**この数値は案件 `260815_01` の実測値である。案件によって変わるので、必ず自分で測る。**
太字の升は、行数が少ないのにバイト数が大きい例——両方測る理由がここにある。

案件フォルダの俯瞰は「見出しだけ」から始める——18 行・982B で、どのファイルがいつ作られた
かが一望できる。走行の順序を示すには、まずこれで足りる。

1本を開くときは `--depth 2` から始める。上の2例ではどちらも 120 行・8KB の内側に収まり、
どんな項目が何件あるかが分かる。そこから読みたい枝を決めて広げる。**いきなり全文を出さない。**

### 4. 大きいものは、保存して添付する

**300 行を超えるもの、または 30KB を超えるもの**は、ファイルに書いて添付し、会話には
要点だけを書く。バイト数だけが超えている場合も同じ扱いにする。

**保存先を案件フォルダにしない。**案件の成果物と紛れる。一時の場所に書く。

```bash
V "$OUT/analysis_output.json" > "<一時の場所>/analysis_output_<案件名>.txt"
```

そのうえで、会話には何を書くか——タスクごとの `task_name`・`causation_claim`・
`n_observations`・`key_finding`、`validity_notes` の `severity` と `concern`、
`has_critical_issues` と `skipped_tasks`。長い `caution` や `interpretation_note` は
添付に譲り、会話では触れるだけにする。

### 5. そこから絞って開く

相手が読みたいものを尋ねる。依頼の文脈から明らかならそのまま開く。
ラウンドの経緯（`.design_changes_*` など）を追うときだけ `--all` を足す。

## 道具の動かし方

`tools/render_json.py` は、**任意の JSON を字下げしたアウトラインに直して表示するだけ**の
道具である。意味づけは一切しない——ファイル名から中身を推し量ることも、スキーマを参照する
ことも、工程順に並べ替えることもしない。

**パスはすべて絶対で書く。**相対パスは、いまいるフォルダが変わると動かない。

```bash
OUT="$LAYER_DIR/projects/<案件名>/output"

# 俯瞰（最初にこれ）
bash "$LAYER_DIR/tools/run" render_json.py "$OUT" --depth 1

# 1本を開く
bash "$LAYER_DIR/tools/run" render_json.py "$OUT/analysis_output.json"

# 内部の記録も含めて全部
bash "$LAYER_DIR/tools/run" render_json.py "$OUT" --all

# 保存する（道具に保存の機能は無い。案件フォルダの外に書く）
bash "$LAYER_DIR/tools/run" render_json.py "$OUT" > "<一時の場所>/review.txt"
```

並ぶ順は**更新時刻の昇順**である。上から読めば、実際に作られた順——つまり走行の順序になる。

ドット始まりのファイル（`.design_round_state.json` など、機構の内部の記録）は、ディレクトリを
走査したときには既定で出ない。パスで名指しした場合は `--all` が無くても出る。

| 終了番号 | 意味 |
|------|------|
| 0 | すべて表示できた |
| 1 | 読めない、または JSON として壊れているファイルがあった（他のファイルの表示は続く） |
| 2 | 使い方の誤り（パスが無い、`*.json` が1件も無い、など） |

## 読むときの手がかり

道具はファイルの意味を知らないので、意味は次の場所で引く。

- **どの工程でどのファイルが出るか** — `playbooks/flow.md`
- **各項目が何を表すか、`correlation_only` や `must_fix` のような値が何を意味するか** —
  `agents_ICD/schemas/` の各スキーマの `description`
- **役の間で何をどう受け渡す約束だったか** — `agents_ICD/`

指摘がどう処理されたかを辿るときは、対にして読む。設計は `design_review_r{N}.json` と
`.design_changes_r{N}.json`、結果検証は `verification_review_r{N}.json` と
`verification_response_r{N}.json` が対になる。

## この道具の対象外

- `report_draft.md` — 本文が Markdown なので、そのまま読む
- `.phase_timing.jsonl` — 専用の `phase_timer.py report` がある
- 生データ（`.csv` / `.xlsx`） — 次節のとおり、扱わない

## 機密性について

この道具が対象とするのは、案件フォルダに置かれる副生成物の JSON——集計値と要約だけを含み、
生の行値を含まない設計のもの——に限られる。生データファイル（`.csv` / `.xlsx`）は読まない。
これは意図的な境界であり、分析層の `CLAUDE.md` → 「守るべき制約」の「情報の機密性」に沿う。
対象を JSON に絞ったのはこの理由による——生データが JSON 形式で案件フォルダに置かれることは
無い設計になっている。

なお、この道具は渡された JSON をそのまま表示する。案件固有の `tables/*.json` を渡す場合は、
その中身が集計値であることを渡す側が確かめること。
